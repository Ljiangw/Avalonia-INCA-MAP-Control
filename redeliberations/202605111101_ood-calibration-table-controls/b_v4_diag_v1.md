# 质量审查报告 — OOD 设计方案 v6

**审查对象**：`a_v4_design_v1.md`（内部版本号 v6）
**审查依据**：`requirement.md`（v3）、`iteration_history.md`（第 1–3 轮反馈）
**审查维度**：需求响应充分度、事实错误/逻辑矛盾、深度与完整性（侧重内部审议未充分覆盖的落地视角）

---

## 审查结论

产出整体架构清晰，前序三轮反馈的核心问题（接口签名缺失、事实错误、空状态边界、键盘导航等）在 v6 中已得到系统性修复。但在**需求折中透明度**、**接口契约完整性**和**编码落地细节**方面仍存在若干可改进项。以下问题按严重程度排列。

## 严重问题

### 问题 1：CubeEditor z 列展示方案与需求存在偏差，未明确标注为需求折中

**问题描述**：
需求 `requirement.md` v3 第 119–125 行明确要求 CubeEditor 表格的 z 轴列"相同 z 值的连续行在 z 列中采用**合并单元格**形式展示，视觉上形成一个 z 切片分组"。设计文档「设计决策 2」直接采用了"z 值每行重复显示 + 视觉分组线"的替代方案，虽然 Avalonia DataGrid V12 原生不支持跨行合并单元格的技术约束成立，但文档未在显著位置明确声明这是**与需求原始意图的有意识折中**，也未说明未来若 Avalonia 支持跨行合并或更换表格组件时的升级路径。实现者阅读文档时可能误以为"每行重复显示"是需求的原始要求，而非替代方案。

**所在位置**：「设计决策 2」小节；对应需求 `requirement.md` 第 119–125 行

**严重程度**：严重

**改进建议**：
1. 在「设计决策 2」开头增加显式声明："因 Avalonia DataGrid V12 原生不支持 `RowSpan` 式跨行单元格，本方案将需求中的'合并单元格'降级为'每行重复显示 + 视觉分组线'，属于与需求原始意图的技术折中。"
2. 补充未来升级路径：若后续 Avalonia 版本引入跨行合并能力，或改用支持合并单元格的自定义表格组件，z 列展示策略可重新评估。

### 问题 2：`ICurveTablePresenter` 接口契约与职责描述不一致（列宽调整能力缺失）

**问题描述**：
文档第 194 行在 `ICurveTablePresenter` 的职责描述中声明"暴露列宽调整能力：实现方可通过拖拽列分隔线调整列宽"，但接口的"关键成员"列表（第 197–204 行）中没有任何与列宽调整相关的成员（如列宽变更事件、最小/最大列宽属性、拖拽启用标志等）。职责描述与接口契约不匹配，下游实现者无法从接口中得知列宽调整的契约入口。

**所在位置**：「核心抽象」→「`ICurveTablePresenter`（接口）」

**严重程度**：一般

**改进建议**：
在 `ICurveTablePresenter` 接口中补充列宽调整相关契约，例如：
- `double MinColumnWidth { get; set; }`
- `event EventHandler<int, double>? ColumnWidthChanged;`（列索引 + 新宽度）
或删除职责描述中的"暴露列宽调整能力"声明，将其降为实现层面的可选能力。

### 问题 4：`IMapData.GetValueMatrix()` / `ICubeData.GetSliceMatrix()` 返回数组的可变性语义未定义

**问题描述**：
文档说明这两个方法"返回二维值矩阵的视图或拷贝"，但未约定调用方对返回数组的修改权限。如果后端返回内部数组的引用视图，而图表实现方或中间层意外修改了数组内容，将破坏后端数据模型的内部一致性。此语义缺失可能导致难以追踪的数据污染问题。

**所在位置**：「核心抽象」→「`IMapData` / `ICubeData`」；「设计决策 15」

**严重程度**：一般

**改进建议**：
1. 在接口文档中明确约定：返回的 `double[,]` 是否为只读。若允许修改，需说明"调用方修改返回数组不会影响后端数据模型"（即必须为拷贝）；若不允许修改，建议标注"调用方不得修改返回数组的内容，否则行为未定义"。
2. 或考虑将返回类型改为更安全的抽象，如 `ReadOnlyMemory2D<double>`（若项目引入 Memory 扩展包），或增加一个 `bool IsReadOnly { get; }` 属性到返回的包装类型中。

### 问题 5：编辑模式下方向键行为未定义

**问题描述**：
「关键行为契约」→「键盘导航行为」定义了方向键在浏览模式（非编辑模式）下的单元格导航行为，但未定义在**编辑模式**下（单元格内 `TextBox` 获得焦点时）按方向键的行为。在编辑模式下，方向键存在两种合理的解释：
1. 在 `TextBox` 内部移动光标（标准文本编辑行为）；
2. 退出编辑并触发单元格导航（Excel 风格）。
此行为缺失将导致交互实现不一致。

**所在位置**：「关键行为契约」→「键盘导航行为」→「通用导航规则」

**严重程度**：一般

**改进建议**：
补充编辑模式下方向键的行为定义。建议采用以下策略（与标定工具的工程工具心智模型一致）：
- **方向键（↑/↓/←/→）**：在 `TextBox` 内部移动光标（标准文本编辑行为），不退出编辑模式。
- **Tab / Enter**：确认输入并退出编辑，同时按相应规则移动焦点（Tab 到下一单元格，Enter 保持在当前单元格）。
- **Esc**：取消编辑并退出编辑模式。

### 问题 6：空状态默认视觉呈现未定义

**问题描述**：
文档定义了空状态的触发条件（`ItemsSource` 为 null、空列表、数据维度为零等）和虚方法 `OnEnterEmptyState()` / `OnExitEmptyState()`，但没有描述基类的**默认实现行为**。如果子类不覆盖这些方法，用户将看到什么？是空白区域、默认占位文本，还是未处理的视觉残留？这直接影响编码实现时的兜底策略。

**所在位置**：「核心抽象」→「`CalibrationEditorBase<T>`（抽象类）」；「错误处理策略」→「数据绑定不匹配错误」

**严重程度**：一般

**改进建议**：
在 `CalibrationEditorBase<T>` 的职责描述中补充默认空状态行为：
- 基类默认在主内容区中央显示 "无有效数据" 占位文本（如使用 `TextBlock`，灰色调，居中）。
- 子类可通过覆盖 `OnEnterEmptyState()` / `OnExitEmptyState()` 自定义视觉呈现。

### 问题 7：数值输入解析策略缺失

**问题描述**：
需求第 161 行要求"输入的数据应能正确解析为数值类型"。设计文档在「输入验证错误」中仅笼统提到"非法字符、越界值"，未定义具体的数值解析规则。标定数据场景中，用户可能输入科学计数法（`1.23e-4`）、带千分位分隔符（`1,000.5`）或本地化小数点（`1,5`）等格式。缺少解析策略将导致不同实现者的解析行为不一致，也可能引发跨文化团队的输入歧义。

**所在位置**：需求 `requirement.md` 第 161 行；设计文档「关键行为契约」→「单元格编辑与数据回写」及「错误处理策略」→「输入验证错误」

**严重程度**：一般

**改进建议**：
在「关键行为契约」中补充数值解析规则：
1. 统一使用 `CultureInfo.InvariantCulture` + `NumberStyles.Float` 进行解析，确保科学计数法支持。
2. 千分位分隔符和本地化小数点**不纳入支持范围**（避免输入歧义），输入包含这些字符时视为验证失败。
3. 定义 `double` 溢出输入（如大于 `double.MaxValue` 的字符串）的处理方式：验证失败，红色边框提示"数值超出范围"。

### 问题 8：`IAsyncSaveCapable.SaveAsync()` 异常语义缺失

**问题描述**：
`IAsyncSaveCapable` 接口定义了 `Task SaveAsync()` 方法，但未约定保存失败时的行为契约：
- 保存失败时应抛出异常还是返回某种结果值？
- 若抛出异常，异常类型是否有约定（如 `InvalidOperationException`、`IOException`）？
- 控件层在调用 `SaveAsync()` 时是否需要捕获异常？捕获后的降级策略是什么？
- `UnsavedChangesChanged` 事件在保存成功后是否触发？保存失败后是否触发？

这些语义缺失将导致后端实现者与控件层的异常处理逻辑无法对齐。

**所在位置**：「核心抽象」→「`IAsyncSaveCapable`（接口）」

**严重程度**：一般

**改进建议**：
1. 明确 `SaveAsync()` 在保存失败时**应抛出异常**，异常类型不限定，但建议文档化常见异常场景（如网络失败、磁盘写入失败）。
2. 控件层调用 `SaveAsync()` 时应使用 `try/catch`，捕获后显示错误提示（如信息栏短暂显示 "保存失败" 红色文本），但**不阻断用户的继续编辑**。
3. 明确 `UnsavedChangesChanged` 的触发语义：仅在 `HasUnsavedChanges` 或 `UnsavedChangeCount` 的实际值发生变化时触发。保存成功后若所有变更已持久化，必须触发一次事件使控件清除脏标记。

### 问题 9：键盘 Tab 导航在 CubeEditor 跨 z 切片边界时的行为未定义

**问题描述**：
「关键行为契约」定义了 Tab 按视觉顺序切换到下一个可编辑单元格、到达行末时自动换到下一行。但在 CubeEditor 中，当用户位于某个 z 切片的最后一个数据单元格时按 Tab，焦点应如何移动？存在多种合理策略：
1. 继续进入下一 z 切片的第一行第一个数据单元格（自然延续）；
2. 停留在当前切片内循环（切片内闭环）；
3. 跳出表格，移动到下一个可聚焦控件（标准 WPF/Avalonia Tab 行为）。
此行为未定义将导致交互实现不一致。

**所在位置**：「关键行为契约」→「键盘导航行为」→「通用导航规则」

**严重程度**：一般

**改进建议**：
明确 CubeEditor 中 Tab 导航到达切片边界时的行为。建议采用策略 1（自然延续到下一 z 切片的第一行），与 DataGrid 的默认行为一致，并在文档中明确说明。若未来引入 z 切片折叠/展开，Tab 行为可重新评估。

### 问题 10：`ISurfaceChartPresenter` 缺少轴标签（名称 + 单位）设置契约

**问题描述**：
需求第 68 行要求折线图"x 轴和 z 轴均显示变量名及单位作为轴标签"，第 91–93 行要求 3D 曲面图"具有 x、y、z 三个坐标轴"。`ILineChartPresenter.LoadData(ICurveData data)` 接收完整的 `ICurveData`，实现方可以从中读取轴名称和单位。但 `ISurfaceChartPresenter.LoadMapData` / `LoadSliceData` 仅接收 `double[,]` 数组和轴值序列（`IReadOnlyList<double>`），**未传递轴名称和单位信息**。`MapEditor`/`CubeEditor` 虽可在内部持有 `IMapData`/`ICubeData` 引用，但 `ISurfaceChartPresenter` 的接口契约中没有任何轴标签设置方法，导致图表实现方无法从接口层面得知应显示什么轴标签。

**所在位置**：「核心抽象」→「`ILineChartPresenter` / `ISurfaceChartPresenter`」

**严重程度**：一般

**改进建议**：
在 `ISurfaceChartPresenter` 中补充轴标签设置契约，例如：
- `void SetAxisLabels(string xName, string xUnit, string yName, string yUnit, string? valueName = null, string? valueUnit = null)`
或改为让 `LoadMapData` / `LoadSliceData` 接收 `IMapData` / `ICubeData` 而非原始数组（但此改动会回退设计决策 15 的优化）。更轻量的方案是增加独立的轴标签设置方法，由 `MapEditor`/`CubeEditor` 在加载数据后调用。

### 问题 12：`ActiveZSliceChangedEventArgs` 缺少 z 轴实际值

**问题描述**：
事件参数仅携带 `OldZIndex` 和 `NewZIndex`，未携带对应的 z 轴实际数值。`CubeEditor` 在 3D 图表标题、状态提示或调试日志中可能需要显示"当前展示 z = 25.5 切片"，此时必须通过 `ICubeData.ZValues[NewZIndex]` 二次查询，增加了调用方与数据模型的耦合。如果事件参数直接携带 z 值，Tracker 的纯逻辑输出将更完整。

**所在位置**：「核心抽象」→「`ActiveZSliceChangedEventArgs`」

**严重程度**：轻微

**改进建议**：
在 `ActiveZSliceChangedEventArgs` 中补充：
- `double OldZValue { get; }`
- `double NewZValue { get; }`
由 `ZSliceActivationTracker` 在触发事件时从 `ICubeData.ZValues` 中读取并填充。

### 问题 13：`ZSliceActivationTracker` 防抖延迟未参数化

**问题描述**：
文档多次提到"100–200ms"防抖延迟（如第 335 行、第 437 行），但 `ZSliceActivationTracker` 的构造函数和关键成员列表中未提供任何可配置防抖延迟的参数。仅提供了 `TimeProvider` 用于测试，但无法调整实际运行时的防抖时长。不同数据量和使用场景下，固定的防抖延迟可能过长或过短。

**所在位置**：「核心抽象」→「`ZSliceActivationTracker`（类）」

**严重程度**：轻微

**改进建议**：
在构造函数中增加 `TimeSpan debounceDelay` 参数，提供合理的默认值（如 `TimeSpan.FromMilliseconds(150)`），使 `CubeEditor` 在实例化 Tracker 时可以按数据量和性能需求调整防抖时间。

### 问题 14：精度展示策略缺少编辑模式下 `TextBox` 初始文本格式定义

**问题描述**：
「精度展示策略」定义了显示格式化规则（`FormatString` 优先，`DisplayPrecision` 后备），但未定义单元格进入编辑模式时 `TextBox` 的初始文本格式。例如：某单元格显示值为 `12.500`（按 `F3` 格式化），用户双击进入编辑时，`TextBox` 应显示 `12.500` 还是 `12.5`（去除末尾零）或 `12.5` 的原始数值？编辑完成后重新显示时又应用什么格式？此细节直接影响用户编辑体验的一致性。

**所在位置**：「关键行为契约」→「精度展示策略」

**严重程度**：轻微

**改进建议**：
补充编辑模式下的格式化规则：
- 单元格进入编辑模式时，`TextBox` 的初始文本使用与显示时相同的格式策略（`FormatString` 或 `DisplayPrecision`），保持用户所见即所得。
- 用户输入完成后，先解析为原始 `double` 数值，再由控件层按格式策略重新格式化显示，确保编辑前后的格式一致性。
- 若 `FormatString` 为空且 `DisplayPrecision` 为 0（或未设置），默认使用 `G6` 格式作为后备，避免显示精度丢失。
